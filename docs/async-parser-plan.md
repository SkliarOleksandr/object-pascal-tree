# План «Асинхронный Парсер»

Статус: согласован 2026-07-20, реализация не начата.
Это канонический план; написан «для себя» — с точностью до полей и инвариантов.
Всё, что помечено `verify:`, — проверить по коду в момент реализации, не принимать на веру.

---

## 0. Цель и рамки

Открытие проекта (.dproj/.dpr/.dpk через Open Project, включая стартовый Sample)
автоматически запускает анализ в фоне, не блокируя UI. Две волны:
сначала ВСЕ модули closure до `IntfReady` (хватает для навигации из других модулей),
затем ВСЕ до `FullReady` (+ cross-пассы). Открытый в редакторе модуль — приоритетно
(цель: полная семантика открытого модуля в пределах 1–3 с, реально — быстрее).
Прогресс done/total с растущим total. Диагностики накапливаются по мере готовности.
Один полный прогон по времени не деградирует (в разумных пределах).

НЕ меняется: синхронные API (`AnalyzeFile/AnalyzeDirectory/AnalyzeProject`) и всё,
что на них сидит — 8 тест-сьютов, корпусные baseline'ы, инструменты, кнопка Parse RTL,
кнопка Run Parse (= отменить фон → синхронный прогон в UI-потоке, тестовый режим).

## 1. Зафиксированные решения (обсуждение 2026-07-20)

1. Статусы модуля: `msQueued → msIntfReady → msFullReady → msCrossReady`
   (юзер назвал IntfReady/FullReady; msCrossReady добавлен мной — см. §4).
2. Отмена: смена/закрытие проекта → Cancel + Wait (drain) всех воркеров.
3. Приоритет открытого модуля — компромиссы допустимы, ставка на скорость.
4. Никакого чекбокса. Две волны intf→full для всех. Main source (.dpr/.dpk/program/
   library — нет interface-секции) — всегда сразу full.
5. ГЛАВНЫЙ ИНВАРИАНТ: парсинг implementation НЕ меняет интерфейсную часть AST.
6. Прогресс — растущий total. Таймер на форме, Interlocked-счётчики.
7. Run Parse — синхронный полный прогон в UI-потоке (для тестов, потом переделаем).

## 2. Ключевые проектные решения (мои, юзер пригласил предлагать)

### 2.1 Снапшоты вместо мутации дерева

НЕ доращивать арену in place: `SetLength` = realloc = старый блок освобождается под
конкурентным читателем → AV. НЕ разделять на два дерева (intf/impl): каждая ссылка
на узел стала бы парой (tree, index) — расползается по RefMap/ExtRefMap/Nav/dump/JSON.

Вместо этого — слот модуля с публикацией неизменяемых снапшотов:

```pascal
TPasModuleStatus = (msQueued, msIntfReady, msFullReady, msCrossReady);

TPasModuleSnapshot = class   // immutable ПОСЛЕ публикации
  Tree: TPasTree;            // владеет TPasPreprocessed (лекс+PP ВСЕГДА whole-file)
  Model: TPasSemaModel;
  IsFull: Boolean;
end;

TPasModuleSlot = class
  Path: string;
  FCurrent: TPasModuleSnapshot;  // читается атомарно (aligned pointer), пишется
                                 // только координатором: build fully → publish
  FStatus: Integer;              // TPasModuleStatus, Interlocked
  FIntfReady, FFullReady: TEvent; // для ЖДУЩИХ фоновых потребителей
end;
```

Гарантия инварианта §1.5: intf-снапшот вообще никогда не трогается; full-снапшот —
НОВЫЙ объект, чья интерфейсная часть побайтно совпадает (см. 2.2). Читатель берёт
`Slot.Current` ОДИН раз на операцию и работает с согласованной парой (Tree, Model).

Отставные снапшоты (intf после публикации full; старые после re-analyze при
редактировании) — в retire-список, освобождаются при закрытии проекта. v1: не
рефкаунтим (intf-дерево ~10–20% от full, память терпима; RTL-масштаб — десятки МБ).
Будущая оптимизация — refcount/epoch, НЕ сейчас.

### 2.2 Stage 2 = перепарс с переиспользованием, НЕ literal resume

Stage 1: лексер + препроцессор по ВСЕМУ файлу (дёшево; снимает проблему $IFDEF,
открытого в interface и закрытого в implementation; Skipped-регионы whole-file —
паритет с хайлайтером), парсер останавливается на top-level токене `implementation`.
Stage 2: полный перепарс тем же visible-стримом (лекс+PP НЕ повторяются) → новое
полное дерево.

Почему не resume: пришлось бы сохранять/восстанавливать состояние билдера
(FPos, открытые родители…) — источник багов; перепарс интерфейсной части стоит
~10–20% парса одного файла (парс — мс на файл), зато результат доказуемо идентичен.

ИНВАРИАНТ ПРЕФИКСА (закрепить тестом, это фундамент всей схемы): парсер
детерминирован и append-only ⇒ узлы full-дерева `[0..N-1]` побайтно равны узлам
intf-дерева, где N = количество узлов intf-дерева, С ДВУМЯ оговорками:
- `Nodes[0]` (nkUnit-корень): `LastToken` различается (intf-дерево кончается раньше);
  сравнивать корень по всем полям, КРОМЕ LastToken;
- у последнего top-level интерфейсного ребёнка в full-дереве `NextSibling`
  указывает на impl-секцию (в intf-дереве NIL_NODE).
`verify:` точный набор расхождений установить по факту первым же memcmp-тестом;
если вылезет что-то ещё — разобраться, а не расширять список исключений вслепую.

Id символов: Collect идёт по дереву в порядке узлов, интерфейс — раньше ⇒ id
интерфейсных символов full-модели совпадают с intf-моделью (тоже закрепить тестом).
Следствие: ExtRefMap других юнитов, указывающий в интерфейс этого юнита
(unitId, symId), остаётся валиден при переходе intf→full. Это и есть выгода схемы.

### 2.3 Правило ожидания: UI не ждёт НИКОГДА

Уточнение юзерского «вызывающий код всегда ждёт минимум IntfReady»:
- UI-поток: `TryGetSnapshot(AMid, AMinStatus, out ASnap): Boolean` — не готово →
  false → экшен disabled / hover no-op. Блокировать UI нельзя — вернём фризы.
- Фоновые потребители (cross-финализатор): ждут `FIntfReady`/`FFullReady`-событий
  с проверкой токена отмены.

### 2.4 Single-writer координатор + чистые воркеры

Воркеры — чистые функции (path, buffer-text, mode) → снапшот; НИКАКОЙ общей мутации.
Вся мутация общего состояния (регистрация юнитов, model id, публикация снапшотов,
постановка follow-up задач) — на одном координаторе. Это продолжение принципа
«parse is a pure function» и снимает 90% вопросов синхронизации.

Model id = порядок регистрации ⇒ в async-режиме НЕдетерминированы между запусками
(порядок открытия closure гонковый). В sync-режиме — как раньше (byte-identical
dump-валидация живёт там). Дампы async-результатов для сравнения сортировать по пути.

## 3. Изменения по файлам

### 3.1 PasTree.Parser.pas — режим «стоп на implementation»

- Новый параметр/флаг парса (напр. `AStopAtImplementation: Boolean`): встретив
  top-level ключевое слово `implementation` (только для unit; program/library/
  package его не имеют — флаг игнорируется, парсим целиком), парсер корректно
  закрывает nkUnit-корень и выходит. `verify:` CollectRoot полагается на форму
  корня (Nodes[0].FirstChild = имя юнита) — intf-дерево обязано её сохранять.
- Ничего больше в парсере не меняется. Никакого resume-состояния.

### 3.2 PasTree.Sema.Model/Resolver — Phase 1 на intf-дереве

- Resolver уже tree-driven; intf-дерево — просто дерево без impl-секции.
  `verify:` пройтись по местам, предполагающим наличие implementation
  (sfHasBody-линковка intf-рутин с impl-телами — на intf-стадии просто не
  произойдёт, это ок: её потребители гейтятся FullReady).
- Тест на id-стабильность: таблица символов intf-модели — префикс full-модели
  (имена + id совпадают).

### 3.3 PasTree.Sema.Project.pas — слоты, статусы, TryGet, per-module cross

- Хранилище моделей: `FModels: TList<...>` → слоты (`TPasModuleSlot`), model id =
  индекс слота. Синхронные Analyze* работают через те же слоты, просто доводят всё
  до msCrossReady последовательно — существующее поведение не меняется.
- `TryGetSnapshot(AMid, AMinStatus, out ASnap)` — публичный API (§2.3).
- Cross-пассы (CrossResolve/CheckCalls/BindTypesX/CrossType) — ПО-МОДУЛЬНО:
  модуль готов к cross, когда сам msFullReady И все его uses ≥ msIntfReady
  (cross смотрит только в ИНТЕРФЕЙСЫ used-юнитов — msIntfReady зависимостей
  достаточно; `verify:` FindMemberX/CrossType ходят по ancestor'ам тоже только
  интерфейсно). BindTypesX/CrossType остаются сериализованными (общая таблица
  generic-инстансов): один «финализатор»-воркер, модули по одному → msCrossReady.
- EnsureSystemUnit/FSystemUnitLock — фолдится в координатор (System — такой же слот).
- E2003-гейтинг (AllUsesResolved) не меняется.

### 3.4 НОВЫЙ PasTree.Sema.Async.pas — сессия, очередь, воркеры, отмена

```pascal
TPasAsyncSession = class
  // создаётся на Open Project, умирает при смене проекта/закрытии
  FCancelled: Integer;              // Interlocked; проверка МЕЖДУ юнитами
  FQueue: приоритетная очередь, 3 полосы:
    P0 = открытый модуль + его прямые uses (intf), затем его cross;
    P1 = intf-волна остального closure (BFS от корней);
    P2 = full-волна (стартует, когда P1 исчерпана);
  FBuffers: TDictionary<string,string>; // снапшоты текстов открытых редакторов,
    // сняты В ГЛАВНОМ ПОТОКЕ до старта / при edit-debounce. SynEdit.Text из
    // воркера читать НЕЛЬЗЯ. SourceManager воркера читает отсюда (SetBuffer
    // per-session, не глобально).
  FTotalDiscovered, FIntfDone, FFullDone: Integer; // Interlocked, для UI-таймера
end;
```

- Корни closure: dproj → FDProj.Files; bare .dpr/.dpk → main source; Sample-режим
  (директория без dproj) → текущий dir-scan список как корни (покрытие не сужаем).
  Closure растёт из uses/contains по мере intf-парсов → FTotalDiscovered растёт.
- Cancel: смена проекта / FormDestroy / Run Parse → `Cancel; WaitDrain;` (bounded),
  потом teardown/synchronous-прогон.
- Ошибки воркеров: складывать в очередь сообщений, дренируемую UI-таймером
  (Log() в контрол из воркера нельзя).
- Пул: default TParallel-пул НЕ подходит для длинной фоновой сессии с приоритетами —
  своя лёгкая очередь + N потоков (N = CPU-1, один резерв UI). `verify:` не
  наступить на грабли TThreadPool.SetMaxWorkerThreads (см. историю с 16-worker пулом).
  `NeverSleepOnMMThreadContention := True` уже стоит в демке (.dpr-уровень).

### 3.5 PasTree.Sema.Nav.pas — кэши по идентичности снапшота

`TNavCache` привязать к снапшоту: хранить ссылку на снапшот, при `CacheOf(AMid)`
сравнить с `Slot.Current` — не совпало → перестроить кэш (VisOfRaw/NodeOfVis/
RoutineOfVis/decl-impl-ключи; индексы узлов между снапшотами intf→full для
ИНТЕРФЕЙСА совпадают, но кэши строятся по всему дереву — проще перестроить целиком).
Это заменяет нынешнее «пересоздать FNav после каждого Analyze».
Деградация на intf-снапшоте зависимости — естественная: клики в интерфейсе работают,
в impl-зоне NodeOfVis пуст → ничего не находится; GotoImplementation не находит
impl-ключей → false → экшен disabled. Специальных гейтов почти не нужно.

### 3.6 Демка (PasTreeDemo.Main.pas)

- Open Project (.dproj/.dpr/.dpk) и стартовый Sample → отменить старую сессию →
  новая TPasAsyncSession. Parse RTL — как есть (sync). Run Parse — Cancel; sync
  Analyze (существующий код, UI блокируется — осознанно, тестовый режим); после
  него async не перезапускается (всё уже msCrossReady).
- Открытие вкладки модуля: подсветка НЕ трогается — хайлайтер уже сам лексит+парсит
  буфер в EnsureFresh, независимо от sema (юзерский пункт «первичный парсинг для
  подсветки в главном потоке» уже выполняется by design). Новое — только бамп
  модуля в P0.
- Edit + 500ms debounce: снять снапшот буфера (main thread) → P0 re-analyze ТОЛЬКО
  этого модуля (intf+full) → fast path: если интерфейсный префикс нового дерева
  идентичен старому (memcmp узлов) — опубликовать, перегнать его собственный cross,
  ГОТОВО (правка в impl — типовой случай, зависимые не трогаем). Если интерфейс
  ИЗМЕНИЛСЯ — опубликовать и перезапустить cross-пассы зависимых (нужен обратный
  индекс Dependents на координаторе, строится при разборе uses) — в фоне.
- Прогресс: `lblProgress` + TTimer (~150 мс): `intf a/N · full b/N` (N растёт);
  скрывать в idle. Тем же таймером дренировать очередь диагностик/сообщений
  (накапливаются по мере msFullReady/msCrossReady).
- FAnalyzing-гард: перестаёт быть нужным в старом смысле; UI-гейт = TryGetSnapshot.

### 3.7 Не трогаем

Лексер, препроцессор (whole-file — уже так), хайлайтер, DProj, все инструменты.

## 4. Матрица «операция → минимальный статус»

| Операция                                   | Модуль          | Статус |
|--------------------------------------------|-----------------|--------|
| Подсветка синтаксиса                        | открытый        | не зависит от sema (свой лексер) |
| Hover/go-to-decl ИЗ модуля                  | открытый        | msFullReady (+cross для внешних имён → msCrossReady) |
| Go-to-decl В зависимость (цель)             | зависимость     | msIntfReady |
| Decl↔impl toggle                            | открытый        | msFullReady (чистый CST-walk) |
| Диагностики модуля (полные)                 | сам             | msCrossReady |
| Cross-пасс модуля (предусловие)             | его uses        | msIntfReady |

## 6. Тесты

1. НОВЫЙ StagedParseSmoke (или в ParserSmoke): (a) intf-дерево == префикс
   full-дерева (memcmp с оговорками §2.2); (b) full-дерево при перепарсе ==
   one-shot full parse (побайтно); (c) program/.dpr: стоп-флаг игнорируется;
   (d) $IFDEF открыт в interface, закрыт в implementation; (e) $I-инклюд,
   пересекающий границу секций; (f) unit БЕЗ implementation-секции вообще
   (легален? `verify:` — если да, intf==full).
2. Sema: id-стабильность (§3.2).
3. НОВЫЙ AsyncSmoke.dpr: fixture-проект → async-сессия → дождаться → дамп
   (сортировка по пути) == sync-дамп; отмена посреди прогона (нет AV/утечек,
   прогнать под ReportMemoryLeaksOnShutdown); edit-fast-path (impl-правка не
   трогает зависимых; intf-правка перегоняет их cross).
4. Все 8 существующих сьютов + корпус — без изменений чисел.

## 7. Порядок реализации (коммиты)

1. Парсер: стоп на implementation + StagedParseSmoke (чистая логика, без потоков).
2. Sema: Phase 1 на intf-дереве + тест id-стабильности.
3. Слоты/снапшоты/статусы в TPasSemaProject + TryGetSnapshot + Nav-кэши по
   снапшоту (драйвер всё ещё синхронный — поведение не меняется).
4. TPasAsyncSession: очередь/воркеры/координатор/отмена + AsyncSmoke (без демки).
5. Демка: авто-парс на Open Project, прогресс-лейбл+таймер, P0-бамп открытого
   модуля, edit-fast-path, гейты экшенов.
6. Перф-валидация против baseline; проверка памяти; полировка.

Каждый коммит — зелёные сьюты + корпус. Пункты 1–3 безопасны и полезны сами по себе.

зависимости грузились одним молчаливым батчем; cross-фаза не репортила ничего
— исправлено: LoadChunked + суб-фазы cross:*); гранулярность отмены = целый
батч (исправлено: проверка между чанками/суб-пассами); .dpr/.dpk-корни дважды
парсились; исключение воркера глоталось молча (LastError + лог в демке);
typer пропускается для транзиентных intf-моделей (ASkipTyper, ключуется по
факту остановки парса, НЕ по флагу — иначе .dpr терял бы диагностику).

СТРУКТУРНЫЙ ОСТАТОК (не баг): staged/batch ≈ 1.45 на RTL-образном коде
(замер: BuildWinRTL.dpk, 317 юнитов, результаты идентичны). Причина: волна 1
(intf parse + Phase 1) для interface-heavy юнитов (Winapi.* = почти весь файл
интерфейс) стоит почти как полная загрузка, а в текущем swap-when-ready
режиме транзиентные intf-модели НИКТО не читает — их цена покупает живой
прогресс и фундамент под live-доступ, но не скорость. Пути вниз (если
понадобится): (а) волна 1 без Phase 1 — uses доставать прямо из дерева,
модель строить только при upgrade (≈1.15–1.2, но IntfReady перестаёт нести
семантическую модель — приемлемо, пока нет live-доступа); (б) resume-parse
волны 2 с префикса intf-арены (§2.2 «настоящий resume») — экономит только
parse-долю интерфейса; (в) полноценный live-доступ к слотам во время сборки
(главный оправдатель всей двухволновой схемы).

## 8. Риски / на что смотреть

- Гонка «читатель со старым снапшотом» — закрыта паттерном build-then-publish +
  retire-список; НЕ освобождать снапшоты до закрытия проекта.
- Порядок памяти при публикации: снапшот полностью построен ДО записи FCurrent;
  запись — через InterlockedExchange(Pointer) (заодно барьер).
- Model id недетерминированы в async (§2.4) — дампы сортировать, ни на что другое
  не влияет.
- Демка держит ссылки на FNav/FSemaProject в обработчиках — все входы через
  TryGetSnapshot, ссылки не кэшировать дольше одной операции.
- Приоритетная инверсия: P2-волна не должна выедать пул при активном P0 —
